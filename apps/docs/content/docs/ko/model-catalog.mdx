LookSee는 런타임 파일시스템에서 ONNX 모델을 검색합니다. API는 워크플로 편집과 검증에
이 카탈로그를 사용하며, 추론 서비스는 동일한 번들을 사용해 레이블을 로드하고 ONNX
세션을 생성합니다.

## 번들 구조

각 모델은 `MODELS_DIR` 아래에 디렉터리 하나를 가집니다:

```text
models/
└── <model-id>/
    ├── model.onnx
    └── manifest.json
```

두 파일 모두 필수입니다. API는 불완전하거나 유효하지 않은 번들을 무시하고 그 이유를
로그로 남깁니다. 모델 ID는 디렉터리 이름이며 다음 조건을 만족해야 합니다:

- 소문자 ASCII 문자, 숫자, `_`, `-`만 포함해야 합니다.
- 1자 이상 64자 이하여야 합니다.
- 모델이 검색된 후에는 변경되지 않아야 합니다.

가중치, 레이블 또는 메타데이터가 변경되면 `dfine-m-fire-v2`처럼 새 ID를
사용하십시오. API와 추론 서비스는 검색된 ID를 프로세스가 살아 있는 동안 캐시하므로,
파일을 제자리에서 교체해도 활성 세션이 안정적으로 갱신되지 않습니다.

모델 파일은 Git에서 무시되며 API 및 추론 컨테이너에 읽기 전용으로 마운트됩니다.

## 매니페스트 스키마

```json
{
  "name": "D-FINE-M Fire and Smoke",
  "labels": ["fire", "other", "smoke"],
  "recommended_confidence_threshold": 0.3,
  "events": {
    "fire": "FIRE_DETECTED",
    "other": null
  }
}
```

| 필드 | 필수 여부 | 의미 |
| --- | --- | --- |
| `labels` | 예 | 클래스 ID를 고유하고 비어 있지 않은 레이블에 매핑 |
| `name` | 아니요 | 표시 이름. 없으면 모델 ID에서 파생 |
| `recommended_confidence_threshold` | 아니요 | 에디터에서 모델을 선택할 때 적용되는 0부터 1 사이의 값 |
| `events` | 아니요 | 레이블-이벤트 재정의. `null`은 해당 레이블을 억제 |

알 수 없는 필드는 거부됩니다. `events`의 모든 키는 `labels`에 존재해야 합니다.

`labels`는 배열 인덱스를 클래스 ID로 사용하는 순서 있는 배열이거나, 0부터 시작하는
연속된 정수 키를 갖는 JSON 객체일 수 있습니다:

```json
{
  "labels": {
    "0": "fire",
    "1": "other",
    "2": "smoke"
  }
}
```

레이블은 고유해야 합니다. 모델이 매니페스트에 없는 클래스 ID를 출력하면 추론
서비스가 오류를 보고합니다.

## 이벤트 매핑

API는 감지된 각 레이블을 의미를 갖는 워크플로 이벤트로 변환합니다:

1. `events`에 해당 레이블이 있으면 설정된 값을 사용합니다.
2. 설정된 값이 `null`이면 해당 레이블에 대한 이벤트를 생성하지 않습니다.
3. 그 외에는 레이블을 대문자로 바꾸고, 영숫자가 아닌 연속 문자를 `_`로 치환한 뒤,
   필요하면 `_DETECTED`를 덧붙입니다.

예를 들어 `space-occupied`는 `SPACE_OCCUPIED_DETECTED`가 됩니다. 이벤트 종류는
대문자로 시작해야 하고, 대문자, 숫자, 밑줄만 포함하며, 길이는 최대 64자여야 합니다.

`GET /models` 응답은 확정된 표시 이름, 클래스, 이벤트 종류, 권장 임계값을
노출합니다. 웹 애플리케이션은 열려 있는 동안 이 카탈로그를 갱신하므로, 프런트엔드를
다시 빌드하지 않아도 새 모델 ID가 나타날 수 있습니다.

## 지원되는 ONNX 시그니처

추론 서비스는 입력 및 출력 텐서의 이름, 타입, 랭크(rank)를 기준으로 어댑터를
선택합니다. 모델 ID로는 절대 분기하지 않습니다. 현재 레지스트리는 두 가지 D-FINE
계약을 지원합니다.

### D-FINE deploy 내보내기

```text
inputs
  images             float tensor, rank 4, three channels, static square size
  orig_target_sizes  int64 tensor, rank 2, final dimension 2

outputs
  labels             int64 tensor, rank 2
  boxes              float tensor, rank 3, final dimension 4
  scores             float tensor, rank 2
```

이 어댑터는 중앙에 배치된 검은색 letterbox로 종횡비를 유지하고, 이미 디코딩된 XYXY
출력을 그대로 사용하며, 박스를 원본 프레임의 픽셀 좌표로 다시 매핑합니다.

### D-FINE raw 내보내기

```text
input
  one float tensor   rank 4, three channels, static square size

outputs
  logits             float tensor, rank 3
  pred_boxes         float tensor, rank 3, final dimension 4
```

이 어댑터는 프레임 크기를 조정하고, 시그모이드를 적용해 점수를 얻고, 쿼리(query)마다
최적 클래스를 선택한 뒤, 정규화된 CXCYWH 박스를 원본 프레임 픽셀 단위의 XYXY 박스로
변환합니다.

카탈로그는 디렉터리와 매니페스트만 검증합니다. ONNX 시그니처는 워크플로가 모델을
처음 요청할 때 추론 서비스가 검증합니다. 지원되지 않거나 모호한 시그니처는 해당
카메라 워커를 오류 상태로 전환하며, 그 시그니처는 추론 로그에 기록됩니다.

## 런타임 동작

- 감지 노드는 `model_id`, 신뢰도(confidence) 임계값, 이벤트 종류, 초당 검사 횟수를
  선택합니다.
- 서로 다른 카메라가 서로 다른 모델을 동시에 사용할 수 있습니다.
- 동일한 모델 ID를 사용하는 카메라들은 추론 프로세스마다 지연 로딩되는 ONNX 세션
  하나를 공유합니다.
- 프로바이더 우선순위는 CUDA(설치된 런타임이 노출하는 경우), 그다음 CPU 순입니다.
- 모델, 신뢰도, 초당 검사 횟수 또는 소스를 변경하면 새로운 펜싱 실행(fenced run)이
  시작됩니다.
- 번들을 제거해도 이미 캐시된 모델은 제거되지 않습니다. ID를 폐기할 때는 의존하는
  워크플로를 중지하고 서비스를 재시작하십시오.

## 아키텍처 어댑터 추가

1. `apps/inference/src/inference/adapters/onnx/models/` 아래에
   `OnnxDetectionAdapter`를 추가합니다.
2. `supports(signature)`에서 전체 텐서 계약을 매칭합니다.
3. 출력을 픽셀 XYXY 박스, 신뢰도 값, 클래스 ID를 담은 `supervision.Detections`로
   변환합니다.
4. `apps/inference/src/inference/adapters/onnx/registry.py`에 해당 타입을 등록합니다.
5. 판별 조건(predicate)은 아키텍처에만 종속되고 모델 ID와는 무관하게 유지합니다.

런타임 명령은 [추론 서비스 가이드](https://github.com/okoflow/looksee/blob/main/apps/inference/README.md)를 참고하십시오.
