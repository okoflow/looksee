LookSee는 미디어 전송, 인식(perception), 워크플로 정책, 프레젠테이션을
분리합니다. 각 서비스는 하나의 경계를 소유하며, 명시적인 HTTP, WebSocket,
MediaMTX 또는 Pydantic 계약을 통해 통신합니다.

## 시스템 컨텍스트

```text
Media plane

+------------------------------------------------+
|    RTSP / RTMP / SRT / WHEP / file / webcam    |
+------------------------+-----------------------+
                         |
                         v
                 +-------+--------+
                 |    MediaMTX    |
                 +-------+--------+
                         |
               +---------+---------+
               | RTSP              | WHEP
               v                   v
       +-------+-------+   +-------+-------+
       |   inference   |   |  web browser  |
       +---------------+   +---------------+

Control and event plane

+-----------+   +--------+   +-----+       HTTP / WebSocket       +-------------+
| inference |<->| Valkey |<->| API |<---------------------------->| web browser |
+-----------+   +--------+   +--+--+                              +-------------+
                                |
                     +----------+----------+
                     | SQL (read/write)    | actions
                     v                     v
              +------+------+   +----------+----------+
              | PostgreSQL  |   | alerts/integrations |
              +-------------+   +---------------------+
```

MediaMTX는 모든 카메라에 안정적인 UUID 경로를 부여합니다. 풀(pull) 소스는
필요할 때 프록시되고, 브라우저 WebRTC 소스는 WHIP을 통해 게시되며, 로컬
파일은 반복 재생되는 스트림으로 실행됩니다. 추론 서비스와 브라우저는 모두
원본 소스 대신 정규화된 MediaMTX 경로를 사용합니다.

## 서비스 경계

| 구성 요소 | 소유하는 것 | 소유하지 않는 것 |
| --- | --- | --- |
| `apps/api` | 워크플로, 그래프 검증과 실행, 카메라의 원하는 상태, 모델 카탈로그, 이벤트, 액션, 알림, 실시간 팬아웃 | 비디오 디코딩과 ONNX 추론 |
| `apps/inference` | 카메라 워커, 프레임 샘플링, ONNX 세션과 어댑터, 신뢰도 필터링, ByteTrack, 감지 출력 | 워크플로 정책과 전달 액션 |
| `apps/studio` | 워크플로 편집, 런타임 구성, 라이브 재생, 오버레이, 이벤트와 알림 표시 | 영구 상태와 서버 측 검증 |
| `packages/shared` | API와 추론 서비스 간 와이어 모델과 모델 매니페스트 스키마 | 애플리케이션 유스케이스 |
| MediaMTX | 스트림 수집, 프로토콜 정규화, WHIP 게시, WHEP 재생 | 감지와 워크플로 상태 |
| PostgreSQL | 영구 저장되는 워크플로, 프로젝션된 카메라, 원하는 상태 명령, 런타임 리비전, 알림 | 일시적인 프레임 |
| Valkey | 명령, 워커 이벤트, 감지 프레임, 만료되는 최신 JPEG | 영구적인 원하는 상태 |

API의 의존성은 안쪽을 향합니다:

```text
+-------------+     +-------------+     +--------+
| entrypoints |---->| application |---->| domain |
+-------------+     +------+------+     +--------+
                           |
                           v
                    +------+------+
                    |  adapters   |
                    +-------------+
```

`domain` 계층의 모델은 FastAPI, SQLAlchemy, Redis 또는 MediaMTX 코드를
임포트하지 않습니다. 추론 서비스에도 이와 유사한 `application`/`adapters`
경계가 있으며, 모델별 동작은 ONNX 어댑터 뒤에 머무릅니다.

## 워크플로 생명주기

워크플로 그래프는 영구 저장되는 문서입니다. 카메라 행은 그래프의
`camera_source` 노드를 프로젝션한 것이며, 워크플로와 노드 ID를 키로
사용합니다.

초안을 저장할 때는 항상 구조적 그래프 인덱스를 빌드합니다. 이 단계에서
중복된 노드 또는 엣지 ID, 대상 없이 매달린(dangling) 엣지, 필터가 아닌
노드에 붙은 분기 메타데이터를 거부합니다. 그래도 초안에는 불완전한 런타임
구성이나 연결되지 않은 노드가 남아 있을 수 있습니다.

워크플로를 활성화하거나 활성화된 워크플로의 그래프를 변경하면 런타임 검사가
추가됩니다:

- 카메라 소스가 최소 하나 존재해야 합니다.
- 소스에서 도달 가능한 그래프에 순환이 없어야 합니다.
- 모든 소스는 정확히 하나의 감지 노드에 도달해야 합니다.
- 도달 가능한 모든 노드는 필수 런타임 필드를 갖추고 있어야 합니다.
- 선택한 모델이 런타임 카탈로그에 존재해야 합니다.
- 선택한 이벤트 종류와 객체 클래스는 도달 가능한 모델에 속해야 합니다.

이 검사 중 하나라도 실패하면 API는 기계가 읽을 수 있는 HTTP `422` 응답을
반환합니다.

## 카메라의 원하는 상태

API는 데이터베이스 변경과 외부 부수 효과를 분리해서 유지합니다:

1. 그래프 인덱스를 빌드하고 검증합니다.
2. 카메라 행을 소스 노드와 재조정(reconcile)하고 각 소스의 추론 구성을
   계산합니다.
3. 워크플로, 카메라, 원하는 시작 명령, 상태, 리비전을 하나의 트랜잭션으로
   커밋합니다.
4. 커밋 후 MediaMTX 경로를 갱신하고 추론 명령을 게시합니다.

추론 구성에는 `model_id`, `confidence_threshold`, `inference_fps`만
포함됩니다. 이 값 중 하나를 바꾸거나 카메라 소스를 변경하면 새로운 원하는
실행(run)이 만들어집니다. 필터, 액션, 이벤트 선택, 레이블, 캔버스 위치를
편집할 때는 그 외 조건이 같다면 활성 상태의 워커가 그대로 유지됩니다.

시작이나 중지가 있을 때마다 카메라의 단조 증가 `revision` 값이 올라갑니다.
또한 시작할 때마다 새로운 `run_id`가 부여됩니다:

- 추론 서비스는 지금까지 확인한 최신 리비전보다 오래된 명령을 무시합니다.
- 특정 실행을 겨냥한 중지는 같은 카메라의 다른 실행을 취소할 수 없습니다.
- API는 워크플로, 리비전, 실행, 모델이 현재의 원하는 상태와 일치하지 않는
  프레임과 워커 이벤트를 무시합니다.

API는 주기적으로 원하는 상태를 다시 로드하고, 누락되거나 고아가 된 MediaMTX
경로를 복구하며, 명령을 다시 게시합니다. 이러한 원하는 상태로의
재조정(reconciliation) 덕분에 Pub/sub 전달은 진실의 원천(source of truth)
역할을 맡지 않으면서 일시적으로 이루어질 수 있습니다.

## 감지 및 이벤트 흐름

1. 워커가 자신의 카메라에 해당하는 MediaMTX RTSP 경로를 확인합니다.
2. 모델 레지스트리가 `models/<model-id>/model.onnx`를 한 번만 로드하고 ONNX
   텐서 시그니처로부터 어댑터를 선택합니다.
3. 워커는 요청된 속도로 프레임을 샘플링하고, 추론을 실행하고, 신뢰도를
   필터링하고, ByteTrack ID를 부착한 뒤 `DetectionFrame`을 게시합니다.
4. API는 저장된 원하는 상태 명령과 대조하여 프레임의 출처를 검증합니다.
5. API는 모델 매니페스트를 사용해 레이블이 붙은 감지를 시맨틱 이벤트 종류로
   묶습니다.
6. 그래프 실행기는 발생지 카메라 노드에서 시작해 필터를 평가하고, 일치하는
   분기를 따라 액션을 실행합니다.
7. API는 감지, 이벤트, 워커 상태, 알림을 해당 카메라의 WebSocket 룸으로
   전송합니다.

모델 레이블은 데이터입니다. 이벤트 오버라이드가 없는 레이블은 결정적인
대문자 `*_DETECTED` 종류가 되고, 오버라이드가 `null`이면 해당 레이블의
이벤트 생성이 억제됩니다. 정확한 규칙은
[모델 카탈로그 레퍼런스](./model-catalog.mdx)를 참고하십시오.

## 그래프 실행

`WorkflowGraphIndex`는 검증과 런타임 실행을 위해 정방향 및 역방향 인접
정보를 한 번만 빌드합니다. 분기가 다시 합류하더라도 각 노드는 파생된
이벤트당 최대 한 번만 실행됩니다.

모든 필터에는 두 가지 결과가 있습니다:

- 일치하면 `if`로 표시된 엣지를 따라갑니다.
- 일치하지 않으면 `else`로 표시된 엣지를 따라갑니다.

분기 메타데이터가 없는 엣지는 일반적인 단일 출력 필터 체인과의 호환성을
위해 `if`처럼 동작합니다. 카메라 소스에서 도달 가능한 순환은 워크플로가
실행되기 전에 거부됩니다.

액션 실패는 노드별로 로그에 기록되며, 이후 노드의 순회를 중단시키지
않습니다. 액션 컨텍스트는 하나의 이벤트 실행 동안 공유되므로, 스냅샷 노드가
이미지 데이터와 URL을 다운스트림 알림 노드에 제공할 수 있습니다.

## Valkey 계약

| 이름 | 전송 방식 | 방향 | 페이로드 |
| --- | --- | --- | --- |
| `stream.commands` | Pub/sub | API에서 추론 서비스로 | `StartStream` 또는 `StopStream` |
| `worker.events` | Pub/sub | 추론 서비스에서 API로 | `WorkerStarted`, `WorkerErrored` 또는 `WorkerStopped` |
| `detection.frames` | 컨슈머 그룹 스트림 | 추론 서비스에서 API로 | `DetectionFrame` |
| `frames.last.<camera_id>` | 만료되는 키 | 추론 서비스에서 API로 | 스냅샷용 최신 JPEG |

정식(canonical) Pydantic 정의는 `packages/shared`에 있습니다. 이 정의들은 알
수 없는 필드를 거부하며, 필요한 곳에는 카메라, 워크플로, 모델, 리비전, 실행
출처 정보를 포함합니다.

## 프런트엔드 경계

웹 애플리케이션은 라우트 어댑터에 Next.js App Router를, 제품 코드에
Feature-Sliced Design을 사용합니다:

```text
+--------------+     +---------+     +----------+     +----------+     +--------+
| _app/_pages  |---->| widgets |---->| features |---->| entities |---->| shared |
+--------------+     +---------+     +----------+     +----------+     +--------+
```

TanStack Query가 REST 서버 상태를 소유합니다. 범위가 지정된 Jotai 스토어가
저장되지 않은 그래프 편집 내용과 선택 상태를 소유하고, React Flow가
캔버스를 렌더링합니다. Zod는 브라우저 경계에서 HTTP와 WebSocket 페이로드를
검증합니다. 슬라이스 간 임포트는 공개 `index.ts` 파일을 사용합니다.

런타임 URL은 요청마다 페이지에 주입됩니다. 브라우저는 API, API WebSocket,
MediaMTX에 직접 연결하므로, 해당 주소는 웹 컨테이너에서만이 아니라
브라우저에서도 접근 가능해야 합니다.

## 운영 제약 사항

- 단일 소유자 계정이 API와 스튜디오를 보호합니다. 테넌트 격리는 없고
  MediaMTX는 여전히 자체 정적 스트림 자격 증명을 사용하므로, 인터페이스는
  신뢰할 수 있는 네트워크를 전제로 합니다.
- MediaMTX 자격 증명은 WHIP과 WHEP 접근을 위해 의도적으로 브라우저에
  노출됩니다.
- WebSocket 룸과 상태 유지(stateful) 필터가 메모리에 있기 때문에 API는
  하나의 프로세스로 실행됩니다.
- 카메라 소스는 하나의 감지 노드에만 도달할 수 있습니다. 다중 모델 팬아웃은
  별도의 워커 아이덴티티가 필요하며 지원되지 않습니다.
- 감지 이력은 일시적입니다. 알림은 영구 저장되며, 스냅샷은 볼륨에 보존됩니다.
- 모델 ID는 프로세스 수명 동안 불변입니다. 가중치를 변경했다면 새 ID로
  게시하십시오.
- Python과 TypeScript 워크플로 스키마는 서비스 경계에서 서로 독립적으로 유지
  관리되며, 반드시 함께 변경되어야 합니다.
