LookSee מפרידה בין שינוע מדיה, תפיסה (perception), מדיניות של תהליכי עבודה
ותצוגה. כל שירות אחראי על גבול אחד ומתקשר באמצעות חוזים מפורשים של HTTP,
WebSocket, MediaMTX או Pydantic.

## מבט-על על המערכת

```text
Media plane

+------------------------------------------------+
|    RTSP / RTMP / SRT / WHEP / file / webcam    |
+------------------------+-----------------------+
                         |
                         v
                 +-------+--------+
                 |    MediaMTX    |
                 +-------+--------+
                         |
               +---------+---------+
               | RTSP              | WHEP
               v                   v
       +-------+-------+   +-------+-------+
       |   inference   |   |  web browser  |
       +---------------+   +---------------+

Control and event plane

+-----------+   +--------+   +-----+       HTTP / WebSocket       +-------------+
| inference |<->| Valkey |<->| API |<---------------------------->| web browser |
+-----------+   +--------+   +--+--+                              +-------------+
                                |
                     +----------+----------+
                     | SQL (read/write)    | actions
                     v                     v
              +------+------+   +----------+----------+
              | PostgreSQL  |   | alerts/integrations |
              +-------------+   +---------------------+
```

MediaMTX מעניק לכל מצלמה נתיב UUID יציב. מקורות משיכה (pull) מועברים דרך פרוקסי
לפי דרישה, מקורות WebRTC מהדפדפן מפרסמים דרך WHIP, וקבצים מקומיים רצים כזרמים
בלולאה. גם שירות ההסקה (inference) וגם הדפדפן צורכים את נתיב ה-MediaMTX המנורמל
במקום את המקור המקורי.

## גבולות השירותים

| רכיב | אחראי על | לא אחראי על |
| --- | --- | --- |
| `apps/api` | תהליכי עבודה, אימות והרצה של גרפים, מצב רצוי של מצלמות, קטלוג המודלים, אירועים, פעולות, התראות, הפצה (fan-out) בזמן אמת | פענוח וידאו והסקה ב-ONNX |
| `apps/inference` | תהליכי worker של מצלמות, דגימת פריימים, סשנים ומתאמים של ONNX, סינון לפי סף ביטחון, ByteTrack, פלט זיהויים | מדיניות תהליכי עבודה ופעולות שליחה |
| `apps/studio` | עריכת תהליכי עבודה, תצורת זמן ריצה, צפייה חיה, שכבות-על, הצגת אירועים והתראות | מצב עמיד (durable) ואימות בצד השרת |
| `packages/shared` | מודלי התקשורת (wire) בין ה-API לשירות ההסקה וסכמת המניפסט של המודלים | תרחישי שימוש (use cases) של האפליקציה |
| MediaMTX | קליטת זרמים, נרמול פרוטוקולים, פרסום ב-WHIP וניגון ב-WHEP | זיהוי ומצב של תהליכי עבודה |
| PostgreSQL | תהליכי עבודה עמידים, הטלות (projections) של מצלמות, פקודות מצב רצוי, רוויזיות של זמן ריצה והתראות | פריימים חולפים |
| Valkey | פקודות, אירועי worker, פריימי זיהוי וקובצי JPEG אחרונים עם תפוגה | מצב רצוי עמיד |

ב-API התלויות מצביעות פנימה:

```text
+-------------+     +-------------+     +--------+
| entrypoints |---->| application |---->| domain |
+-------------+     +------+------+     +--------+
                           |
                           v
                    +------+------+
                    |  adapters   |
                    +-------------+
```

מודלים של שכבת ה-`domain` אינם מייבאים קוד של FastAPI, SQLAlchemy, Redis או
MediaMTX. לשירות ההסקה יש הפרדה דומה בין `application` ל-`adapters`, והתנהגות
ספציפית למודל נשארת מאחורי מתאמי ONNX.

## מחזור החיים של תהליך עבודה

גרף של תהליך עבודה הוא מסמך עמיד. שורות המצלמות הן הטלות של צומתי
ה-`camera_source` שלו, והמפתח שלהן הוא צירוף של תהליך העבודה ומזהה הצומת.

שמירת טיוטה תמיד בונה אינדקס מבני של הגרף. בנייה זו דוחה מזהים כפולים של צמתים
או קשתות, קשתות תלושות (dangling) ומטא-נתוני ענף על צמתים שאינם מסננים. טיוטה
עדיין יכולה להכיל תצורת זמן ריצה חלקית או צמתים מנותקים.

הפעלה של תהליך עבודה, או שינוי הגרף של תהליך עבודה מופעל, מוסיפים בדיקות זמן
ריצה:

- קיים לפחות מקור מצלמה אחד.
- הגרף הנגיש ממקור חסר מעגלים.
- כל מקור מגיע לצומת Detect אחד בדיוק.
- לכל צומת נגיש מוגדרים שדות זמן הריצה הנדרשים לו.
- המודל שנבחר קיים בקטלוג זמן הריצה.
- סוגי האירועים ומחלקות האובייקטים שנבחרו שייכים למודלים נגישים.

ה-API מחזיר תגובת HTTP `422` קריאה למכונה כאשר אחת מהבדיקות האלה נכשלת.

## מצב רצוי של מצלמות

ה-API מפריד בין שינויים בבסיס הנתונים לבין תופעות לוואי חיצוניות:

1. בניית אינדקס הגרף ואימותו.
2. התאמה (reconciliation) של שורות המצלמות לצומתי המקור וחישוב תצורת ההסקה של
   כל מקור.
3. ביצוע commit של תהליך העבודה, המצלמות, פקודות ההפעלה הרצויות, הסטטוס
   והרוויזיות בטרנזקציה אחת.
4. לאחר ה-commit, עדכון נתיבי MediaMTX ופרסום פקודות הסקה.

תצורת ההסקה מכילה רק את `model_id`, `confidence_threshold` ו-`inference_fps`.
שינוי של אחד מהערכים האלה או של מקור המצלמה יוצר ריצה רצויה חדשה. עריכה של
מסננים, פעולות, בחירת אירועים, תוויות או מיקומים על הקנבס משאירה worker פעיל
על כנו.

כל הפעלה או עצירה מקדמת את ה-`revision` המונוטוני של המצלמה. כל הפעלה גם מקבלת
`run_id` חדש:

- שירות ההסקה מתעלם מפקודות ישנות מהרוויזיה החדשה ביותר שראה.
- עצירות ממוקדות אינן יכולות לבטל ריצה אחרת באותה מצלמה.
- ה-API מתעלם מפריימים ומאירועי worker שתהליך העבודה, הרוויזיה, הריצה או המודל
  שלהם אינם תואמים את המצב הרצוי הנוכחי.

ה-API טוען מחדש את המצב הרצוי מעת לעת, מתקן נתיבי MediaMTX חסרים או יתומים
ומפרסם מחדש פקודות. לכן המסירה ב-Pub/sub יכולה להיות חולפת, מבלי שהיא הופכת
למקור האמת.

## זרימת זיהויים ואירועים

1. ה-worker מאתר את נתיב ה-RTSP של המצלמה שלו ב-MediaMTX.
2. מרשם המודלים טוען את `models/<model-id>/model.onnx` פעם אחת ובוחר מתאם לפי
   חתימת הטנזורים של ה-ONNX.
3. ה-worker דוגם פריימים בקצב המבוקש, מריץ הסקה, מסנן לפי ביטחון, מצרף מזהי
   ByteTrack ומפרסם `DetectionFrame`.
4. ה-API מאמת את מוצא הפריים (provenance) מול פקודת המצב הרצוי השמורה.
5. ה-API משתמש במניפסט המודל כדי לקבץ זיהויים מתויגים לסוגי אירועים סמנטיים.
6. מנוע ההרצה של הגרף מתחיל בצומת המצלמה שממנו נוצר האירוע, מעריך את המסננים
   ומריץ פעולות לאורך ענפים תואמים.
7. ה-API שולח זיהויים, אירועים, סטטוס worker והתראות לחדר ה-WebSocket של
   המצלמה.

תוויות המודל הן נתונים. דריסת אירוע (override) חסרה הופכת לסוג דטרמיניסטי
באותיות רישיות מהצורה `*_DETECTED`, ואילו דריסת `null` משתיקה את יצירת האירוע
לאותה תווית. לכללים המדויקים ראו את
[מדריך העזר של קטלוג המודלים](./model-catalog.mdx).

## הרצת הגרף

`WorkflowGraphIndex` בונה פעם אחת רשימות שכנות (adjacency) קדימה ולאחור, לצורך
אימות והרצה בזמן ריצה. כל צומת מורץ לכל היותר פעם אחת לכל אירוע נגזר, גם כאשר
ענפים מתמזגים.

לכל מסנן יש שתי תוצאות:

- התאמה ממשיכה לאורך קשתות המסומנות `if`.
- אי-התאמה ממשיכה לאורך קשתות המסומנות `else`.

קשת ללא מטא-נתוני ענף מתנהגת כמו `if`, לשם תאימות עם שרשראות מסננים רגילות
בעלות פלט יחיד. מעגלים נגישים ממקורות מצלמה נדחים לפני שתהליך עבודה יכול לרוץ.

כשלים בפעולות נרשמים ביומן לכל צומת בנפרד ואינם עוצרים את המעבר על הצמתים
הבאים. הקשר (context) של הפעולות משותף במהלך הרצה אחת של אירוע, וכך צומת
Snapshot (תמונת מצב) יכול לספק נתוני תמונה וכתובת URL לצומתי הודעות במורד
הזרם.

## חוזי Valkey

| שם | תעבורה | כיוון | מטען |
| --- | --- | --- | --- |
| `stream.commands` | Pub/sub | מה-API לשירות ההסקה | `StartStream` או `StopStream` |
| `worker.events` | Pub/sub | משירות ההסקה ל-API | `WorkerStarted`, `WorkerErrored` או `WorkerStopped` |
| `detection.frames` | זרם עם קבוצת צרכנים (consumer group) | משירות ההסקה ל-API | `DetectionFrame` |
| `frames.last.<camera_id>` | מפתח עם תפוגה | משירות ההסקה ל-API | ה-JPEG האחרון עבור תמונות מצב |

הגדרות ה-Pydantic הקנוניות נמצאות ב-`packages/shared`. הן דוחות שדות לא מוכרים
וכוללות נתוני מוצא של מצלמה, תהליך עבודה, מודל, רוויזיה וריצה בכל מקום שבו
הדבר נדרש.

## גבולות הפרונטאנד

אפליקציית הווב משתמשת ב-App Router של Next.js עבור מתאמי נתיבים
וב-Feature-Sliced Design עבור קוד המוצר:

```text
+--------------+     +---------+     +----------+     +----------+     +--------+
| _app/_pages  |---->| widgets |---->| features |---->| entities |---->| shared |
+--------------+     +---------+     +----------+     +----------+     +--------+
```

TanStack Query אחראי על מצב השרת של REST. store מתוחם (scoped) של Jotai מחזיק
בעריכות הגרף שטרם נשמרו ובבחירה, בעוד React Flow מרנדר את הקנבס. Zod מאמת
מטעני HTTP ו-WebSocket בגבול הדפדפן. ייבוא בין slices נעשה דרך קובצי
`index.ts` ציבוריים.

כתובות ה-URL של זמן הריצה מוזרקות לעמוד בכל בקשה. הדפדפן מתחבר ישירות ל-API,
ל-WebSocket של ה-API ול-MediaMTX, ולכן הכתובות האלה חייבות להיות נגישות
מהדפדפן — לא רק מקונטיינר הווב.

## אילוצים תפעוליים

- חשבון בעלים יחיד מגן על ה-API ועל הסטודיו; אין בידוד בין דיירים (tenants),
  ו-MediaMTX עדיין משתמש בפרטי גישה סטטיים משלו לזרמים, ולכן הממשקים מניחים
  רשת מהימנה.
- פרטי הגישה של MediaMTX חשופים לדפדפן במכוון, לצורך גישה ב-WHIP וב-WHEP.
- ה-API רץ כתהליך יחיד, מפני שחדרי ה-WebSocket והמסננים שומרי המצב (stateful)
  נמצאים בזיכרון.
- מקור מצלמה יכול להגיע לצומת Detect אחד. הפצה (fan-out) לכמה מודלים דורשת
  זהות worker אחרת ואינה נתמכת.
- היסטוריית הזיהויים חולפת. התראות הן עמידות, ותמונות מצב נשמרות ב-volume.
- מזהי מודלים אינם ניתנים לשינוי לאורך חיי התהליך. פרסמו משקולות ששונו תחת
  מזהה חדש.
- סכמות תהליכי העבודה ב-Python וב-TypeScript מתוחזקות בנפרד בגבולות השירותים
  וחייבות להשתנות יחד.
