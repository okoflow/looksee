LookSee разделяет транспорт медиа, распознавание, политику воркфлоу и представление.
Каждый сервис владеет одной границей и взаимодействует через явные контракты HTTP,
WebSocket, MediaMTX или Pydantic.

## Системный контекст

```text
Media plane

+------------------------------------------------+
|    RTSP / RTMP / SRT / WHEP / file / webcam    |
+------------------------+-----------------------+
                         |
                         v
                 +-------+--------+
                 |    MediaMTX    |
                 +-------+--------+
                         |
               +---------+---------+
               | RTSP              | WHEP
               v                   v
       +-------+-------+   +-------+-------+
       |   inference   |   |  web browser  |
       +---------------+   +---------------+

Control and event plane

+-----------+   +--------+   +-----+       HTTP / WebSocket       +-------------+
| inference |<->| Valkey |<->| API |<---------------------------->| web browser |
+-----------+   +--------+   +--+--+                              +-------------+
                                |
                     +----------+----------+
                     | SQL (read/write)    | actions
                     v                     v
              +------+------+   +----------+----------+
              | PostgreSQL  |   | alerts/integrations |
              +-------------+   +---------------------+
```

MediaMTX даёт каждой камере стабильный UUID-путь. Pull-источники проксируются по
требованию, WebRTC-источники из браузера публикуются через WHIP, а локальные файлы
работают как зацикленные потоки. И инференс, и браузер используют нормализованный путь
MediaMTX вместо исходного источника.

## Границы сервисов

| Компонент | Отвечает за | Не отвечает за |
| --- | --- | --- |
| `apps/api` | Воркфлоу, валидация и выполнение графа, желаемое состояние камер, каталог моделей, события, действия, алерты, рассылка в реальном времени | Декодирование видео и ONNX-инференс |
| `apps/inference` | Воркеры камер, сэмплирование кадров, ONNX-сессии и адаптеры, фильтрация по уверенности, ByteTrack, вывод детекций | Политика воркфлоу и действия доставки |
| `apps/studio` | Редактирование воркфлоу, настройка рантайма, живое воспроизведение, оверлеи, отображение событий и алертов | Долговременное состояние и серверная валидация |
| `packages/shared` | Wire-модели между API и инференсом и схема манифеста модели | Сценарии использования слоя «application» |
| MediaMTX | Приём потоков, нормализация протоколов, публикация WHIP и воспроизведение WHEP | Состояние детекций и воркфлоу |
| PostgreSQL | Долговременные воркфлоу, проекции камер, желаемые команды, рантайм-ревизии и алерты | Временные кадры |
| Valkey | Команды, события воркеров, кадры детекций и последние JPEG с истекающим сроком | Долговременное желаемое состояние |

API следует правилу зависимостей, направленных внутрь:

```text
+-------------+     +-------------+     +--------+
| entrypoints |---->| application |---->| domain |
+-------------+     +------+------+     +--------+
                           |
                           v
                    +------+------+
                    |  adapters   |
                    +-------------+
```

Модели слоя «domain» не импортируют код FastAPI, SQLAlchemy, Redis или MediaMTX. В
инференсе есть похожая граница между слоями «application» и «adapters», а поведение,
специфичное для конкретной модели, остаётся за ONNX-адаптерами.

## Жизненный цикл воркфлоу

Граф воркфлоу — это долговременный документ. Строки камер являются проекциями его нод
`camera_source`, а их ключом служат воркфлоу и ID ноды.

Сохранение черновика всегда строит структурный индекс графа. Он отклоняет повторяющиеся
ID нод и рёбер, висячие рёбра и метаданные ветвления на нодах, не являющихся фильтрами.
Черновик при этом может содержать неполную рантайм-конфигурацию или несвязанные ноды.

Включение воркфлоу или изменение графа уже включённого воркфлоу добавляет
рантайм-проверки:

- Существует хотя бы один источник камеры.
- Граф, достижимый из источника, ацикличен.
- Каждый источник достигает ровно одной ноды детекции.
- Каждая достижимая нода имеет все обязательные рантайм-поля.
- Выбранная модель существует в рантайм-каталоге.
- Выбранные виды событий и классы объектов принадлежат достижимым моделям.

Когда одна из этих проверок не проходит, API возвращает машиночитаемый ответ HTTP `422`.

## Желаемое состояние камер

API разделяет изменения в базе данных и внешние побочные эффекты:

1. Строит и валидирует индекс графа.
2. Выполняет реконсиляцию строк камер с нодами-источниками и вычисляет конфигурацию
   инференса для каждого источника.
3. Фиксирует воркфлоу, камеры, желаемые команды запуска, статус и ревизии в одной
   транзакции.
4. После фиксации транзакции обновляет пути MediaMTX и публикует команды инференсу.

Конфигурация инференса содержит только `model_id`, `confidence_threshold` и
`inference_fps`. Изменение одного из этих значений или источника камеры создаёт новый
желаемый запуск. Редактирование фильтров, действий, выбора событий, меток или позиций на
холсте сохраняет уже активный воркер.

Каждый запуск или остановка увеличивает монотонную `revision` камеры. Каждый запуск
также получает новый `run_id`:

- Инференс игнорирует команды старше самой новой ревизии, которую он видел.
- Адресные остановки не могут отменить другой запуск на той же камере.
- API игнорирует кадры и события воркеров, чьи воркфлоу, ревизия, запуск или модель не
  соответствуют текущему желаемому состоянию.

API периодически перечитывает желаемое состояние, восстанавливает отсутствующие или
осиротевшие пути MediaMTX и повторно публикует команды. Поэтому доставка через pub/sub
может быть эфемерной, не становясь при этом источником истины.

## Поток детекций и событий

1. Воркер определяет RTSP-путь MediaMTX своей камеры.
2. Реестр моделей один раз загружает `models/<model-id>/model.onnx` и выбирает адаптер по
   сигнатуре ONNX-тензоров.
3. Воркер сэмплирует кадры с запрошенной частотой, выполняет инференс, фильтрует по
   уверенности, присваивает идентификаторы ByteTrack и публикует `DetectionFrame`.
4. API сверяет происхождение кадра с сохранённой желаемой командой.
5. API использует манифест модели, чтобы сгруппировать размеченные детекции в
   семантические виды событий.
6. Исполнитель графа начинает с исходной ноды камеры, вычисляет фильтры и запускает
   действия вдоль совпавших веток.
7. API отправляет детекции, события, статус воркера и алерты в WebSocket-комнату камеры.

Метки модели — это данные. Отсутствующее переопределение события превращается в
детерминированный вид `*_DETECTED` в верхнем регистре, а переопределение `null` подавляет
создание события для этой метки. Точные правила описаны в
[справочнике по каталогу моделей](./model-catalog.mdx).

## Выполнение графа

`WorkflowGraphIndex` один раз строит прямую и обратную смежность для валидации и
выполнения в рантайме. Каждая нода выполняется не более одного раза для каждого
производного события, даже когда ветки сходятся.

У каждого фильтра два исхода:

- Совпадение идёт по рёбрам с пометкой `if`.
- Несовпадение идёт по рёбрам с пометкой `else`.

Ребро без метаданных ветвления ведёт себя как `if` — для совместимости с обычными
цепочками фильтров с одним выходом. Циклы, достижимые из источников камер, отклоняются до
того, как воркфлоу сможет запуститься.

Сбои действий логируются по каждой ноде и не прерывают обход последующих нод. Контекст
действий общий на время выполнения одного события, что позволяет ноде снапшота передать
данные изображения и URL нижестоящим нодам уведомлений.

## Контракты Valkey

| Имя | Транспорт | Направление | Полезная нагрузка |
| --- | --- | --- | --- |
| `stream.commands` | Pub/sub | Из API в инференс | `StartStream` или `StopStream` |
| `worker.events` | Pub/sub | Из инференса в API | `WorkerStarted`, `WorkerErrored` или `WorkerStopped` |
| `detection.frames` | Стрим с группой потребителей | Из инференса в API | `DetectionFrame` |
| `frames.last.<camera_id>` | Ключ с истекающим сроком | Из инференса в API | Последний JPEG для снапшотов |

Канонические определения Pydantic находятся в `packages/shared`. Они отклоняют
неизвестные поля и там, где это требуется, включают сведения о происхождении: камеру,
воркфлоу, модель, ревизию и запуск.

## Границы фронтенда

Веб-приложение использует Next.js App Router для адаптеров маршрутов и Feature-Sliced
Design для продуктового кода:

```text
+--------------+     +---------+     +----------+     +----------+     +--------+
| _app/_pages  |---->| widgets |---->| features |---->| entities |---->| shared |
+--------------+     +---------+     +----------+     +----------+     +--------+
```

TanStack Query владеет серверным REST-состоянием. Scoped-хранилище Jotai владеет
несохранёнными правками графа и выделением, а React Flow отрисовывает холст. Zod
валидирует полезные нагрузки HTTP и WebSocket на границе браузера. Импорты между слайсами
идут через публичные файлы `index.ts`.

Рантайм-URL внедряются в страницу при каждом запросе. Браузер подключается напрямую к
API, WebSocket API и MediaMTX, поэтому эти адреса должны быть доступны из браузера, а не
только из веб-контейнера.

## Эксплуатационные ограничения

- Единственный аккаунт владельца защищает API и studio; изоляции тенантов нет, а MediaMTX
  по-прежнему использует собственные статические учётные данные потоков, поэтому
  интерфейсы рассчитаны на доверенную сеть.
- Учётные данные MediaMTX намеренно видимы браузеру для доступа по WHIP и WHEP.
- API работает как один процесс, потому что WebSocket-комнаты и фильтры с состоянием
  находятся в памяти.
- Источник камеры может достигать одной ноды детекции. Разветвление на несколько моделей
  требует отдельной идентичности воркера и не поддерживается.
- История детекций эфемерна. Алерты долговременны, а снапшоты сохраняются в томе.
- ID моделей неизменяемы в течение времени жизни процесса. Публикуйте изменённые веса под
  новым ID.
- Схемы воркфлоу на Python и TypeScript сопровождаются независимо на границах сервисов и
  должны меняться вместе.
